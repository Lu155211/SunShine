CodecLab：把视频编解码做成一条可解释的系统

2026 年 8 月 14 日 · 12 分钟阅读 · GitHub 源码

视频转码很容易被描述成一个命令：输入文件，选择编码器，得到输出文件。但真正需要长期维护的工具，不能只关心“能不能输出”，还要回答三个问题：这一帧经过了哪些路径？失败发生在哪一层？画质指标到底在衡量什么？

CodecLab 是我用 Android、C++、FFmpeg 和 MediaCodec 搭起来的一个实验室。它的核心目标不是隐藏复杂性，而是把复杂性分层、命名并留下可验证的边界。

一条清晰的分层边界

Android UI / File Picker / Task Queue
          │
          ├── MediaCodec：硬件解码、硬件编码、Surface 播放
          │
          └── JNI → libcodec_core.so
                         ├── FFmpeg demux / decode / scale
                         ├── x264 / x265 software encode
                         ├── Annex-B + MP4 output
                         └── PSNR + libvmaf metrics

上层 Java 负责平台工作：选择文件、管理应用私有目录、串行调度批量任务、展示进度和播放结果。Native 核心负责媒体工作：探测输入、执行软件编解码、生成裸流和预览 MP4，以及计算客观指标。

两层之间不共享 FFmpeg 的内部结构体，而是通过字符串 JSON 的 C ABI 传递请求和响应。这样 JNI 很薄，未来把同一个核心接到 iOS 的 Objective-C++ 或 Swift bridge 时，也不需要把 FFmpeg 的版本细节暴露给上层。

四种组合，四条明确的路径

“硬件”与“软件”不是一个可以随时偷偷切换的实现细节，而是用户对任务的明确选择。CodecLab 将解码器和编码器拆开，形成四种组合：

解码编码实现帧边界
软件软件FFmpeg → x264 / x265Native 内存
软件硬件FFmpeg → MediaCodec临时 NV12
硬件软件MediaCodec → x264 / x265临时 YUV
硬件硬件MediaCodec → MediaCodec内存中的 YUV

混合组合使用任务目录中的临时 YUV 文件作为阶段边界，成功或失败后都会清理。没有“硬件失败就自动改成软件”的隐式降级：如果用户选择的实现不可用，系统返回明确错误。这样结果才可复现，性能和画质比较才有意义。

为什么硬件转码不能只读一个 YUV 平面

Android 硬件解码的难点不只是调用 MediaCodec。不同设备可能返回不同的颜色格式、stride 和 slice-height；某些厂商还会把 UBWC 或 tiled 布局包装成看似普通的 YUV_420_888。如果按照紧凑的线性平面直接读取，就可能得到绿色花屏或错位画面。

CodecLab 的转码硬解路径使用 MediaCodec.getOutputImage() 获取线性输出，并根据真实的平面信息复制 Y、U、V 数据；硬编码则在启动后读取实际协商的颜色格式和对齐参数，再把输入 YUV 写入编码器。播放是另一条路径：硬件解码器直接输出到 SurfaceView，避免 ImageReader、Bitmap 和额外的 YUV 往返。

播放为什么与转码分开

预览的首要目标是低延迟和稳定渲染，不是暴露每一帧给算法。因此播放优先使用 MediaExtractor → MediaCodec → SurfaceView，在开始解码前预读视频尺寸，完成等比例布局，让硬件解码器直接把帧交给 Surface。

如果设备的硬件播放配置失败，才回退到原有的 MediaPlayer + TextureView 路径。这个回退只影响预览，不会改变用户在转码任务中选择的编码实现。

指标先定义参考，再谈“画质”

预编码 YUV ──► 编码器 ──► preview.mp4 ──► 解码器
     │                                      │
     └──────────── PSNR / VMAF ────────────┘

如果直接把“原视频文件”当作参考，指标会混入原始解码器、旋转、缩放和抽帧方式的差异。CodecLab 保存编码器实际收到的预编码 YUV，再把编码后 MP4 解码为输出帧，按顺序配对计算 PSNR，并用内置 vmaf_v0.6.1 模型计算 VMAF。

报告用 metricBasis=pre_encode_yuv_vs_decoded_output 标记这一基准。移动端默认每 2 帧采样一次 VMAF，把计算成本控制在可接受范围；批量任务结束后，再对成功文件做算术平均，同时展示有效文件数和统计帧数。

可复现比“看起来能跑”更重要

工程将 FFmpeg、x264、x265 和 libvmaf 的版本锁定在 third_party/DEPENDENCIES.lock，并通过脚本定义源码准备、媒体库构建和 Android 链接边界。日常 Android Studio Run 使用已发布的媒体包做完整性校验，不会每次启动都重编译第三方源码。

与此同时，构建产物、CMake 中间目录、Gradle 缓存、本地 SDK 配置和第三方源码缓存都不应该进入版本库。仓库保存的是能解释系统、重建依赖和定位问题的源代码与文档，而不是某台机器的临时状态。

从 Android 走向跨平台

CodecLab 的跨平台策略从 ABI 开始：保持核心 C ABI 向后兼容，新增配置只增加 JSON 字段，旧调用方可以忽略新响应。迁移到 iOS 时，软件编解码和指标路径可以复用；Android 的 MediaCodec 后端替换为 VideoToolbox，平台 UI 则由 SwiftUI 或 UIKit 负责。

这也是我对“架构”的理解：不是提前抽象出一套漂亮的目录，而是在真正的边界上做出可测试、可替换、可解释的选择。

CodecLab 的完整工程与构建说明已放在 GitHub 仓库。如果你关心的不只是最终的 MP4，而是每一帧如何走过系统、每一个分数如何产生，这个项目就是一份可以继续拆开的答案。
